このドキュメントは、Androidタスク管理アプリ「CHECKLIST」のアーキテクチャ、
タスクのライフサイクル、状態遷移、発生した不具合、実施した修正ロジック、
および実機検証結果をまとめたものです。
他のLLM（Claude、Gemini Argon等）が本仕様書を読み、異なる観点から
エッジケースや潜在的な設計リスクのセカンドオピニオン検証を行うことを目的としています。


1. アプリケーション概要と設計思想

[1-1] 基本情報
- アプリ名: CHECKLIST
- パッケージ名: com.k11301440.checklist
- プラットフォーム: Android (minSdk 26, targetSdk 35, Jetpack Compose)
- 保存形式: 単一JSONファイル (checklist_data.json) によるアトミック保存 (AtomicFile)

[1-2] 設計思想 (航空チェックリスト思想)
- SpaceXや航空機コクピットの計器・チェックリストUIに着想を得たミニマル設計。
- 認知負荷を極限まで低減するため、一般的なTODOアプリのような「無限の未完了タスク一覧」を持たない。
- 1日を4つの時間帯フェーズ（01 朝, 02 午前, 03 午後, 04 夜）に分割。
- 各フェーズで「今やるべきタスク」だけに集中し、未完了の重要タスクは次フェーズへ持ち越す（キャリーオーバー）。


2. データモデル構造

[2-1] ChecklistItem (タスク)
- id: String (UUID)
- title: String (タスク名)
- priority: Priority (REQUIRED: 重要 / OPTIONAL: 標準)
- isCompleted: Boolean (完了フラグ)
- isDeleted: Boolean (破棄/ゴミ箱フラグ)
- scheduledDate: String? (YYYY-MM-DD形式)
- scheduledPhase: Int? (フェーズインデックス 0..3)
- sortOrder: Int (フェーズ内の並び順)
- originPhaseIndex: Int (発生元フェーズインデックス 0..3)

[2-2] PhaseData (フェーズ)
- id: String (例: "phase_morning", "phase_forenoon", "phase_afternoon", "phase_night")
- name: String (例: "朝", "午前", "午後", "夜")
- isCompleted: Boolean (フェーズ自体の完了フラグ)
- items: List<ChecklistItem> (そのフェーズに登録されているタスクリスト)

[2-3] AppSettings (設定)
- carryOverTasks: Boolean (重要タスクを次フェーズへ引き継ぐか)
- carryOverStandardTasks: Boolean (標準タスクも引き継ぐか)
- autoAdvanceByTime: Boolean (時刻に応じたフェーズ自動進行)
- enableSwipePhaseSwitch: Boolean (左右スワイプによるフェーズ切替)
- notificationDisplayMode: NotificationDisplayMode (OFF / COUNT_ONLY / COUNT_AND_TITLE)
- largeButtonMode: Boolean (大きなボタン表示)


3. タスクライフサイクルと状態遷移

[3-1] 通常作成
- ユーザーが画面下部の入力バーからタスクを追加。
- 指定されたフェーズ（または現在のフェーズ）の items に追加される。
- 新規追加時、originPhaseIndex にはそのフェーズの index が設定される。

[3-2] 状態変更アクション
- 完了 (completeItem): チェックボックスをタップ。isCompleted = true に遷移。
- 完了解除 (undoItem): 完了済みタスクを長押し。isCompleted = false に遷移。
- 破棄 (removeItem): ゴミ箱ボタンをタップ。isDeleted = true に遷移 (論理削除)。
- 復元 (restoreItem): 破棄済みタスクの「RESTORE」をタップ。isDeleted = false に遷移。
- 完全消去 (clearCompletedItems): 完了・破棄されたタスクをリストから完全除外。

[3-3] キャリーオーバー (次フェーズへの引き継ぎ)
- フェーズを完了して次のフェーズへ進む際 (completePhase):
  - 未完了の重要タスク (settings.carryOverTasks == true)
  - または未完了の標準タスク (settings.carryOverStandardTasks == true)
  を次のフェーズへコピーする。
- 表示上は「CARRYOVER // 朝」のように発生元フェーズ名が付与される。


4. 過去に発生したバグと原因分析

[4-1] バグ1: キャリーオーバー後の元タスク完了が他フェーズへ反映されずタスクが増殖する
- 現象:
  朝フェーズでタスクを作成 -> 未完了のまま午前フェーズへ進みキャリーオーバー発生
  -> 朝フェーズに戻ってタスクを完了
  -> 午前フェーズのキャリーオーバー側タスクが未完了のまま残り、タスクが2重に存在してしまう。
- 原因:
  各フェーズが独立した ChecklistItem インスタンスを保持しており、
  あるフェーズで isCompleted を true にしても、他フェーズにコピーされた
  同一タスク（同一IDまたは同名タスク）に状態変更が伝播していなかった。

[4-2] バグ2: キャリーオーバータスクを完了後、前後にフェーズ移動すると未完了に巻き戻る
- 現象:
  午前フェーズでキャリーオーバーされたタスクを完了にする
  -> 朝フェーズに戻る
  -> 再び午前フェーズに進む
  -> 完了したはずのタスクが再び未完了状態に戻ってしまう。
- 原因:
  フェーズを切り替えた際、あるいはフェーズ完了処理が再評価された際に、
  元フェーズの未完了情報や古い状態から再コピーが走り、
  新フェーズで完了にした状態が上書きされてしまっていた。


5. 実施した改修内容 (Single Source of Truth 整合エンジン)

[5-1] 自動整合エンジン (reconcileTaskStates)
ChecklistRepository 内に、データ保存直前および取得時に必ず走る
状態整合性自動検証・同期エンジンを実装。

ロジックの要点:
(1) 全フェーズの全タスクを横断走査。
(2) 同一ID、または「同一タイトルかつキャリーオーバー関係」にあるタスク群をグループ化。
(3) グループ内で一度でも「isCompleted = true」になったタスクがあれば、
    そのグループの全タスクを強制的に isCompleted = true に同期。
(4) グループ内で一度でも「isDeleted = true」になったタスクがあれば、
    そのグループの全タスクを強制的に isDeleted = true に同期。
(5) 同一フェーズ内に同一IDまたは同一内容のタスクが重複して存在する場合、1件に統合（重複排除）。
(6) タイトルや優先度の変更もグループ全体で最新の内容に統一。

[5-2] 操作時の全フェーズ一括更新
completeItem, undoItem, removeItem, restoreItem, updateItem, clearCompletedItems の
各メソッドにおいて、該当フェーズだけでなく全フェーズの同一タスクを一括で同期更新。

[5-3] completePhase の冪等化
次フェーズへキャリーオーバーする際、次フェーズに既に同一IDのタスク、
または同一タイトルの未完了タスクが存在する場合は再生成をスキップ。
完了済みタスクを未完了で上書きしないようガード条件を厳格化。


6. 実機（エミュレータ）での検証結果ログ

2026年10月18日、Android 15 (API 36) 実機エミュレータにて以下の検証を完遂。

(1) 朝フェーズで新規重要タスク「TASK_A」を作成。
    - 状態: 朝フェーズに「重要タスク残り 1 件」「TASK_A」が正常登録。

(2) 未完了のまま右上の三点メニューから「次のフェーズへ」を実行。
    - 状態: 午前フェーズに自動遷移。
    - 表示: 午前フェーズに「CARRYOVER // 朝」「TASK_A」が正常に引き継がれたことを確認。

(3) 朝フェーズに戻り、「TASK_A」のチェックボックスをタップして完了。
    - 状態: 朝フェーズで「未処理のタスクなし」「完了・破棄されたタスク」内に取り消し線付きで移動。
    - ボタン表示が「フェーズ完了済み (再確認)」に更新。

(4) 午前フェーズに切り替え。
    - 状態: 午前フェーズの「TASK_A」も自動的に「完了・破棄されたタスク」に同期完了！
    - 未処理タスクなし、タスクの増殖なし、未完了の取り残しが完全に解消されたことを確認。

(5) 前後移動による巻き戻り耐性テスト。
    - 午前フェーズ（完了状態）から朝フェーズへ移動、さらに午前フェーズへ戻る。
    - 状態: TASK_A は完了状態を完全に維持。未完了に巻き戻らないことを実機スクリーンショットで確認。

(6) UI・設定項目の実機検証。
    - 左右スワイプによるフェーズ切替アニメーション (AnimatedContent) 動作確認。
    - カレンダー画面での月送り・逆戻り防止ガード (10月以前へのスワイプ抑止) 動作確認。
    - 設定画面での3段階通知トグル (OFF -> 件数のみ -> 件数とタスク名) 動作確認。
    - 大きなボタン表示トグル (OFF -> ON でボタン拡大) 動作確認。
    - ユーザーサポート・テスターお問い合わせ欄の表示確認。


7. セカンドオピニオン (Claude / Gemini Argon) に検証してほしい観点

以下のエッジケースや潜在リスクについて、コードベースおよびデータフローの観点から
検証およびフィードバックを行ってください。

[7-1] 複数フェーズを連続でまたぐキャリーオーバー
- 朝で作成したタスクを未完了のまま午前 -> 午後 -> 夜と連続で引き継いだ場合、
  途中のフェーズ（例: 午後）で完了または削除した際、朝・午前・夜の全インスタンスに
  破綻なく同期されるか。

[7-2] 複数日にまたがるタスク（カレンダー・翌日への引き継ぎ）
- 「翌日に進む」を実行した際、前日の完了済みログと翌日へ持ち越されたタスクの
  IDや状態が衝突・意図しない上書きを起こさないか。

[7-3] 同名タスクの意図的な作成時の衝突可能性
- ユーザーが意図して「朝」と「午後」に同じ名前（例: 「メール確認」）で
  独立した別々のタスクを作成した場合、キャリーオーバー関係がないにもかかわらず
  同名判定によって誤って状態が同期されてしまわないか。
  (ChecklistItem.originPhaseIndex と id の照合ロジックの妥当性)

[7-4] ウィジェット更新とアプリ本体更新の並行性 (Race Condition)
- ホーム画面ウィジェット側からのタスク完了操作と、アプリ本体側からの操作が
  短時間で重複した場合、単一JSONファイルへの書き込み競合や不整合が発生しないか。

[7-5] データ蓄積とガベージコレクション
- 過去のフェーズで完了・削除されたタスクデータがJSON内に残り続けることによる
  ファイル肥大化やパフォーマンスへの影響、およびクリア処理の安全性。


8. セカンドオピニオン検証結果および追加改修内容 (2026年10月19日)

[8-1] 検証項目 [7-1] 複数フェーズを連続でまたぐキャリーオーバー
- 発見した課題:
  (a) 朝 -> 午前 -> 午後 -> 夜と多段持越した際、従来の completePhase は毎回
      sourcePhaseName を直前フェーズ名で上書きしていたため、元の発生フェーズ名（朝）が失われていた。
  (b) resetPhase で単一フェーズのみ未完了に戻すと、reconcileTaskStates の完了OR合成によって
      他フェーズに残る完了済みコピーから即座に完了状態へ巻き戻る問題があった。
  (c) 重要タスクウィジェット (CriticalTasksWidgetProvider) が全フェーズから未完了重要タスクを
      収集する際、キャリーオーバーされた同一IDタスクを重複排除しておらず、多段持越時に
      同じタスクが複数回カウント・表示される問題があった。
- 実施した修正:
  (a) TaskSync.selectCarryover にて、既に isCarryover == true のタスクは元の sourcePhaseName を維持。
  (b) resetPhase でも同一IDの全フェーズインスタンスを一括で未完了へ戻すよう修正。
  (c) WidgetUpdateHelper.buildTaskListWidget にて distinctBy { it.id } による重複排除を追加。

[8-2] 検証項目 [7-2] 複数日にまたがるタスク（カレンダー・翌日への引き継ぎ）
- 発見した課題:
  (a) 翌日遷移時 (buildNextDayState)、前日にキャリーオーバーされたコピー (isCarryover == true) が
      テンプレート未設定時に全フェーズのベース項目としてそのまま残り、翌日に複数フェーズへ増殖したり、
      完了済みの持越タスクや単発日付指定タスクが翌日に未完了として復活したりする問題があった。
  (b) 午後・夜などで作成した未完了タスクが翌朝 (index = 0) へ持越される際、元のフェーズ (index > 0)
      にも重複して残る問題があった。
  (c) 最終フェーズで「1日の全フェーズを完了」(completePhase) を実行した際、最終フェーズ内のタスクしか
      翌日持越対象にしておらず、スワイプや自動進行で途中フェーズをスキップしていた場合に
      朝・午前・午後の未完了重要タスクが翌日に引き継がれない問題があった。
  (d) DailyRecord 作成時およびカレンダー画面の「本日のリアルタイム状況」にて、フェーズ横断の
      キャリーオーバーコピーが重複カウントされていた。
  (e) 「明日」「明後日」を指定して追加した予約タスクが、追加当日のフェーズ一覧にも即時表示されていた。
- 実施した修正:
  (a) TaskSync.buildNextDayState にて、isCarryover == true の一時コピーおよび完了済みの当日以前予約タスクを
      翌日のベース項目から除外し、未完了持越タスクは翌朝フェーズの先頭へ1件のみ集約。
  (b) 翌朝へ引き継がれる未完了タスクID (carryoverIds) は index > 0 のベース項目から除外し二重化を防止。
  (c) completePhase の最終フェーズ完了時も TaskSync.collectDayCarryover で全フェーズの未完了タスクを集約。
  (d) TaskSync.createDailyRecord および CalendarScreen のライブ集計で ID 単位のユニーク集計に統一。
  (e) AppState に scheduledItems (ScheduledTask リスト) を新設し、未来日付タスクは指定日到来時
      (releaseDueScheduled) までフェーズ一覧に出さないよう分離。旧データの未来タスクも自動移行。

[8-3] 検証項目 [7-3] 同名タスクの意図的な作成時の衝突可能性
- 発見した課題:
  (a) isSameOrCarryoverTask、reconcileTaskStates、clearCompletedItems がタイトル一致を併用していたため、
      ユーザーが「朝」と「午後」に意図して同名の独立タスク（例: 「メール確認」）を作成した場合や、
      片方がキャリーオーバーを持った瞬間に別タスクまで完了・削除・消去が連動してしまう問題があった。
  (b) 同一フェーズ内に同名の非キャリーオーバータスクを追加すると reconcileTaskStates で2件目以降が
      消失する問題があった。
  (c) 次フェーズに同名の「完了済み」タスクが存在すると、未完了タスクのキャリーオーバーがスキップされていた。
- 実施した修正:
  (a) キャリーオーバー時は元のタスクID (UUID) をそのまま保持してコピーする設計とし、
      状態同期・整合エンジン・完了消去のすべてを「ID一致のみ」に統一。同名でも別IDの独立タスクは一切干渉しない。
  (b) 同一フェーズ内の重複排除も ID 一致のみに変更。
  (c) TaskSync.mergeCarryover では、次フェーズに同一IDが存在する場合、または同一タイトルの「未完了」タスクが
      存在する場合のみスキップするよう厳格化。

[8-4] 検証項目 [7-4] ウィジェット更新とアプリ本体更新の並行性 (Race Condition)
- 発見した課題:
  (a) persist() が毎回 Dispatchers.IO 上で並列にコルーチンを起動していたため、短時間に連続操作すると
      checklist_state.json.tmp への書き込み競合や、古いスナップショットによる新しい状態の逆転上書きが
      起こり得る構造だった。
  (b) loadInitialState() 内で _appState 初期化完了前に persist() を呼ぶ経路があり、マイグレーション発生時に
      NullPointerException が発生するリスクがあった。
- 実施した修正:
  (a) ChecklistRepository に Dispatchers.IO.limitedParallelism(1) の単一書き込みディスパッチャと
      AtomicLong による世代番号 (writeVersion) を導入。書き込みを完全に直列化し、後続の更新がある場合は
      古いスナップショットのファイル出力をスキップ。
  (b) 初期ロード時は initialStateNeedsSave フラグのみを立て、_appState 初期化後の init ブロックで安全に保存。

[8-5] 検証項目 [7-5] データ蓄積とガベージコレクション
- 発見した課題:
  (a) dailyRecords と reviewLogs に上限がなく、長期運用時に JSON ファイルが肥大化し続ける構造だった。
  (b) loadInitialState 時に reconcile が走っておらず、また予約タスクが削除済みでも残る可能性があった。
- 実施した修正:
  (a) TaskSync に MAX_DAILY_RECORDS (400日分) および MAX_REVIEW_LOGS (1000件) の上限プルーニングを実装。
  (b) 起動時にも TaskSync.reconcile と releaseDueScheduled を適用し、削除済み予約タスクも自動除外。
  (c) TaskSyncTest (全14ケース) を作成し、[4-1][4-2] および [7-1]〜[7-5] の全シナリオをJUnitで自動検証済み。
